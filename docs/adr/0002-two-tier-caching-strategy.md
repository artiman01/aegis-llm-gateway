# ADR 0002: Two-Tier Caching Architecture (L1 Exact Hash + L2 Semantic Cosine Similarity)

- **Status:** Accepted
- **Date:** 2026-10-02
- **Author:** Principal Software Architect
- **Deciders:** Core Engineering Team

---

## 1. Context and Problem Statement

Production LLM interactions incur significant financial cost and high user-perceived latency (typically 400ms to 4000ms per request). In high-throughput enterprise gateways, a large proportion of inference queries are either:
1. **Identical requests:** Repetitive prompts from user interfaces, batch pipelines, or automated agents.
2. **Semantically equivalent requests:** Queries with trivial syntactic variations, synonym substitutions, or whitespace disparities that convey identical user intent (e.g., *"How do I reset my password?"* vs. *"Guide me to reset password"*).

A single-tier exact-match cache fails to capture semantic duplicates, leading to suboptimal cache hit ratios (< 15%). Conversely, relying solely on vector similarity search introduces vector index lookup latency, embedding compute overhead, and the risk of **false-positive semantic matches** (returning an answer that addressed a different question).

AegisLLM requires an optimal caching architecture that minimizes latency, maximizes cache hit ratios, and prevents semantic drift.

---

## 2. Decision Drivers

- **Sub-millisecond Latency on Exact Hits:** Exact matches should be returned in under 1ms, completely bypassing embedding inference.
- **Semantic Capture:** Semantically equivalent queries should achieve cache hits without triggering expensive upstream LLM calls.
- **Zero Hallucination / False-Positive Protection:** Critical differences in query intent (e.g. negation, distinct IDs) must not be conflated.
- **Fail-Open Operational Safety:** Cache unavailability (Redis outage or embedding failure) must never fail client requests; traffic must transparently pass through to upstream LLMs.
- **Storage & Invalidation Manageability:** Memory bounds, TTL-based eviction, and client-controlled cache bypass headers.

---

## 3. Decision: Hierarchical Two-Tier Cache Pipeline

We adopt a **Two-Tier (L1 / L2) Caching Strategy**:

```
Client Request
      │
      ▼
┌──────────────┐       HIT (< 1ms)
│   L1 Exact   ├─────────────────────────────► Return Cached Response
│  (SHA-256)   │                               (Tier: L1 Exact)
└──────┬───────┘
       │ MISS
       ▼
┌──────────────┐
│  Embedding   │ Local ONNX FastEmbed (all-MiniLM-L6-v2, 384-dim)
│  Generation  │ Latency: ~5-12ms on CPU
└──────┬───────┘
       │
       ▼
┌──────────────┐  Cosine Similarity >= 0.90
│ L2 Semantic  ├─────────────────────────────► Return Cached Response
│    Cache     │                               (Tier: L2 Semantic)
└──────┬───────┘
       │ MISS
       ▼
┌──────────────┐
│ Upstream LLM │ Provider Call (OpenAI / Anthropic / Fallback)
└──────┬───────┘
       │
       ▼
  Async Populate L1 & L2 Caches
```

### 3.1 Tier 1: L1 Exact Match Cache
- **Mechanism:** In-Memory dictionary / Redis key-value store using deterministic SHA-256 hashes generated by `ChatCompletionRequest.compute_cache_key()`.
- **Key Formulation:**
  $$\text{Key} = \text{SHA256}(\text{Canonicalize}(\text{model}, \text{messages}, \text{temperature}, \text{top\_p}, \text{tools}))$$
- **Complexity & Latency:** $O(1)$ lookup, $< 1\text{ms}$.
- **False Positive Probability:** $0\%$ (exact cryptographic collision resistance).
- **Default TTL:** 3,600 seconds (1 hour).

### 3.2 Tier 2: L2 Semantic Similarity Cache
- **Mechanism:** Vector representation generated via local ONNX runtime (`FastEmbed` utilizing `sentence-transformers/all-MiniLM-L6-v2`, 384-dimensional dense vectors) followed by Cosine Similarity evaluation over candidates for the designated model.
- **Cosine Similarity Formula:**
  $$\text{similarity}(u, v) = \frac{u \cdot v}{\|u\|_2 \|v\|_2}$$
  Because FastEmbed vectors are $L_2$-normalized upon inference, this simplifies to pure inner product:
  $$\text{similarity}(u, v) = \sum_{i=1}^{d} u_i \cdot v_i$$
- **Latency:** ~5ms to 15ms total (embedding generation + vector scan).
- **Default TTL:** 86,400 seconds (24 hours).

## 4. Addressing False Positives and Threshold Calibration

The primary risk of semantic caching is returning a cached answer to a question that differs in critical nuances (e.g., *"Show order #101"* vs *"Show order #102"* or polarity inversion *"Why is Python slow?"* vs *"Why is Python NOT slow?"*).

### 4.1 Similarity Threshold Selection Matrix

| Threshold ($\tau$) | Semantic Match Precision | Cache Hit Ratio | Risk Profile | Recommendation |
| :--- | :--- | :--- | :--- | :--- |
| **$\ge 0.95$** | Near 100% | Low (~18-25%) | Extremely safe, conservative | High-risk financial/medical domains |
| **$0.90 - 0.94$** | **~98.5%** | **Optimal (~35-50%)** | **Balanced, enterprise-grade** | **AegisLLM Default ($\tau = 0.90$)** |
| **$0.80 - 0.89$** | ~82% | High (~60%) | Notable risk of contextual mismatch | General QA / brainstorming only |
| **$< 0.80$** | $< 65\%$ | Aggressive | Unacceptable semantic drift | Strictly prohibited |

### 4.2 Guardrails Against False Positives
1. **Model Scope Partitioning:** L2 semantic search is strictly partitioned by virtual model name (`model == target_model`). A response generated by `gpt-4o-mini` is never served for a `gpt-4o` request.
2. **Temperature Awareness:** When `temperature > 0.0`, clients often expect stochastic diversity. AegisLLM allows configuring strict cache bypass for requests where `temperature > 0.7`.
3. **Structured Tool/Function Call Exclusion:** Requests containing `tools` or `functions` definitions bypass L2 semantic caching by default to avoid stale parameter invocations.
4. **Client-Controlled Invalidation Header:** Downstream services can force a cache bypass using standard HTTP headers:
   `Cache-Control: no-cache` or `X-Aegis-No-Cache: true`.

---

## 5. Invalidation Strategy and Memory Bounds

1. **TTL-Driven Expiration:**
   - Both L1 and L2 caches enforce individual TTLs. L1 uses a shorter window (e.g. 1 hour) for rapidly changing contexts, while L2 maintains longer residency (e.g. 24 hours).
2. **Bounded In-Memory Eviction:**
   - For in-memory adapters, maximum entry limits (e.g. 50,000 keys) are enforced via Least Recently Used (LRU) eviction to prevent out-of-memory (OOM) conditions.
3. **Fail-Open Error Handling:**
   - If Redis is disconnected or FastEmbed throws an inference exception, the `SemanticCacheService` logs a warning, emits a Prometheus metric (`record_cache_access(tier, hit=False)`), and seamlessly falls back to upstream provider dispatch.

---

## 6. Consequences

### Positive
- **Latency Drop:** 95% latency reduction on exact cache hits (<1ms vs 1200ms).
- **Cost Reduction:** Drastic reduction in token consumption and API billing for high-frequency queries.
- **Provider Protection:** Shields upstream providers from throttling and sudden traffic spikes.

### Negative & Mitigations
- **CPU Overhead for Embeddings:** FastEmbed ONNX runs on CPU. Mitigated by checking L1 first; embedding is only computed on L1 cache misses.
- **Memory Footprint:** Normalized embeddings require 384 `float32` values (1.5 KB per entry). 100,000 cached prompts consume ~150 MB RAM, which is negligible for modern server environments.
